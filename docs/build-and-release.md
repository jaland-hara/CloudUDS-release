# Сборка и выпуск: из чего и как собирается CloudUDS

Этот документ отвечает на вопросы: из какого исходного кода собран выпуск, откуда берутся сторонние компоненты, пакеты и
конфигурации, где и как идёт сборка, как выпуск подписывается и попадает к заказчику, и как проверить происхождение
конкретной установки. Пошаговые команды сборки — [«Сборка пакета выпуска вручную»](bundle-build.md).

## 1. Путь от исходников до установки

```
исходники                 сборка                         выпуск                          установка
─────────                 ──────                         ──────                          ─────────
репозиторий cloududs ─┐
(наш код, патчи,      │   сборочная машина (Docker):     пакет cloududs-X.Y.Z.tar        ВМ установщика:
 Dockerfile, роли)    ├─► образы контейнеров ─────────►  + manifest.json (sha256)  ───►  install.sh проверяет
upstream-проекты      │   + код ролей и мастера          + manifest.sig (Ed25519)        подпись и суммы →
на закреплённых       │   + агент UDS, клиенты           GitHub Releases                 мастер установки →
коммитах и версиях ───┘                                  репозитория выпусков            узлы проекта VK Cloud
                                   ▲
                       подпись манифеста — на отдельной
                       машине с ключом (не на сборочной)
```

- Всё, что работает на узлах в контейнерах, приходит **только из пакета выпуска**: узлы не скачивают образы из
  интернета и не используют реестры образов.
- Из интернета при установке узлы берут **только пакеты Ubuntu 24.04** из зеркал (раздел 5).
- Пакет подписан. `install.sh` проверяет подпись и контрольную сумму каждого файла **до** распаковки; изменённый после
  выпуска пакет не установится.

## 2. Репозитории

| Репозиторий | Доступ | Что в нём |
|---|---|---|
| `jaland-hara/cloududs` | приватный | весь наш код: кабинет и портал, мастер установки, роли узлов, агенты; патчи к upstream-проектам; Dockerfile образов; скрипты сборки и публикации; справка кабинета (из неё собирается эта документация) |
| `jaland-hara/CloudUDS-release` | публичный | `install.sh`, открытый ключ проверки подписи `release-pub.pem`, документация `docs/`, заметки к выпускам; пакеты выпусков — во вложениях GitHub Releases |

Каждый выпуск привязан к коммиту приватного репозитория: коммит записан в манифест пакета (поле `git`) и в описание выпуска
на GitHub.

## 4. Что входит в пакет выпуска

### 4.1. Образы контейнеров

| Образ | Базовый образ | Что внутри | Откуда зависимости |
|---|---|---|---|
| `broker` | `ubuntu:24.04` | брокер OpenUDS 5 + наши патчи и модули | пакеты Ubuntu; Python-зависимости — PyPI по `requirements.txt` брокера на закреплённом коммите |
| `panel` | `python:3.12-slim-bookworm` | кабинет администратора и портал сотрудников (один образ, два контейнера), агенты для столов и узлов | пакеты Debian; PyPI по `panel/backend/requirements.txt` |
| `installer` | `python:3.12-slim-bookworm` | мастер установки | пакеты Debian; PyPI по `installer/requirements.txt` |
| `tunnel` | сборка `rust:1-bookworm`, работа `debian:bookworm-slim` | туннель UDS | crates.io по `Cargo.lock` проекта; список зависимостей лежит в образе (`/usr/share/cloududs/Cargo.lock`) |
| `guacamole` | сборка `maven:3-eclipse-temurin-17`, работа `tomcat:9.0-jdk21-temurin-noble` | шлюз HTML5: Guacamole 1.6.0 + вход по билету UDS | Maven Central; пакеты Ubuntu |
| `guacd` | `debian:bookworm-slim` | guacd 1.6.0 из исходников Apache, FreeRDP 2 из Debian | пакеты Debian |
| `dbproxy` | `haproxy:2.8` | локальный прокси брокера к Galera | пакеты Debian (обновления поверх базового образа) |
| `keepalived` | `alpine:3.22` | keepalived для VIP пары туннелей | пакеты Alpine |
| `memcached` | — | `memcached:1.6-alpine` с Docker Hub без изменений | — |

Базовые образы берутся с Docker Hub (официальные образы). При каждой сборке в образы ставятся обновления пакетов ОС новее
базового образа (`apt-get upgrade` / `apk upgrade`).

### 4.2. Агент UDS и клиенты сотрудников

Собираются отдельно от образов и кладутся в пакет готовыми файлами:

| Что | Где собирается | Чем |
|---|---|---|
| агент UDS для Linux (`udsactor-linux.tgz`) | Linux-машина сборки | Rust (cargo + zig, цель glibc 2.24 — для Astra) |
| агент UDS для Windows (`udsactor-win64.zip`) | Windows-машина сборки | Rust |
| клиент для Windows (`UDSLauncher-5.0.0-win64.zip`) | Windows-машина сборки | Visual Studio Build Tools, Rust, vcpkg (zlib, OpenSSL, FFmpeg, libusb, OpenH264, cJSON), MIT Kerberos |
| клиент для macOS (`UDSLauncher-5.0.0.pkg`) | Mac | Homebrew (OpenSSL, krb5), Rust |
| клиенты для РЕД ОС 8 и Astra SE 1.8 (`.rpm`, `.deb`) | ВМ РЕД ОС | пакеты РЕД ОС; для Astra — сборщик upstream на Debian 12 в Docker |
| клиент для Альт p11 (`.rpm`) | ВМ Альт | пакеты Альт |

Во всех клиентах — FreeRDP 3.27.1 с нашими патчами (раздел 3). Портал раздаёт клиентов сотрудникам из пакета выпуска,
кабинет раздаёт агент UDS команде подготовки образа.

### 4.3. Код установки

`code.tar.gz`: мастер установки, скрипты ролей узлов (`deploy/roles`), служебные инструменты (`deploy/tools`), шаблон
конфигурации кабинета, схемы архитектуры. Исходников брокера и кабинета в нём нет — они внутри образов.

### 4.4. Манифест и подпись

`manifest.json` — версия, коммит, время сборки, SHA-256 и размер каждого файла пакета, для каждого образа — имя, тег и
ID. `manifest.sig` — подпись манифеста ключом Ed25519. Закрытый ключ хранится вне сборочной машины: манифест передаётся к
ключу, подпись — обратно. Открытый ключ — `release-pub.pem` в репозитории выпусков, он же вписан в `install.sh`.

> Сейчас выпуски подписаны ключом разработки (версии `0.x.y-…`). Ключ для выпусков в эксплуатацию будет заменён и
> объявлен в репозитории выпусков.

## 5. Что ставится из пакетов Ubuntu

На узлы мастер ставит пакеты из зеркал Ubuntu 24.04 (зеркало VK Cloud, при недоступности — `archive.ubuntu.com`, при
необходимости — через прокси организации):

| Узлы | Пакеты |
|---|---|
| все | обновления безопасности и ядро (полное обновление при установке), далее — автоматические обновления Ubuntu |
| брокеры, туннели, шлюзы HTML5, внешние туннели, ВМ «всё в одном» | `docker.io`, `docker-compose-v2` |
| фронты | `haproxy`, `keepalived` (у пары) |
| узлы БД | `mariadb-server`, `galera-4`, `mariadb-backup` |
| узлы, подключаемые из кабинета (туннели, шлюзы, пограничные фронты) | то, чего нет на узле: `docker.io` для контейнеров, `python3-cryptography` для агента фронтов |
| ВМ установщика | `docker.io`, `zstd`, `curl` |

Версии этих пакетов определяет Ubuntu, обновляются они штатно (мастер, «Обновить ОС узлов»).

## 6. Откуда конфигурации

Готовых конфигураций из интернета продукт не берёт. Все настройки создаются при установке и в работе:

| Что | Откуда |
|---|---|
| параметры установки (профиль инсталляции, адреса, имена, бакеты, учётные записи облака) | вводит администратор в мастере; хранятся на ВМ установщика (`/var/lib/cloududs-installer`) |
| секреты установки (пароли баз, ключи UDS, мастер-ключ кабинета, пароль VRRP, SSH-ключ к узлам, корень сертификатов установки) | генерирует мастер; хранятся зашифрованными на ВМ установщика, на узлы попадают только нужные (файлы с правами 0600) |
| конфигурации узлов: HAProxy, keepalived, Galera, стек брокера, туннели | пишут скрипты ролей из пакета по параметрам мастера |
| конфигурация кабинета | шаблон из пакета + параметры мастера |
| объекты UDS: подключение облака, транспорты, аутентификаторы, менеджеры ОС | создают мастер (шаг «Настройки кабинета») и кабинет через REST API брокера |
| сертификаты сайта, белые списки, защита входа, сертификаты узлов (mTLS) | хранит кабинет; на фронты и узлы их раскладывают агенты `vdi-certsync` и `vdi-nodeagent` |

## 7. Обращения в интернет во время работы

| Кто | Куда | Зачем |
|---|---|---|
| узлы | зеркала Ubuntu (или прокси организации) | пакеты ОС и обновления безопасности |
| кабинет | Let's Encrypt (ACME) и DNS-провайдер (VK Cloud DNS или Cloudflare) | выпуск и продление сертификатов сайта, если выбран Let's Encrypt |
| кабинет, брокер | API VK Cloud (в опции vSphere — vCenter) | создание столов, питание, сети, VIP, записи DNS |
| кабинет | api.osv.dev | проверка описи пакетов узлов и образов на известные уязвимости («Уязвимости») |
| ВМ установщика | github.com (репозиторий выпусков) | загрузка пакета новой версии; без доступа пакет можно принести файлом |

## 8. Сборка

- **Где:** отдельная сборочная машина Linux amd64 с Docker (BuildKit). Код на неё копируется из рабочей копии на нужном
  коммите; подпись выпуска на ней не делается.
- **Как:** каждый образ собирается своим Dockerfile из репозитория; сторонние исходники клонируются на закреплённом
  коммите или скачиваются по закреплённой версии с проверкой SHA-256 (раздел 3).
- **Свежесть:** окончательные выпуски и не реже раза в неделю — полная пересборка без кэша слоёв (`--pull --no-cache`):
  свежие базовые образы и пакеты ОС, закрываются известные уязвимости. Загрузки PyPI, crates.io и Maven при этом берутся
  из кэша сборочной машины, если версия не изменилась.
- **Состав пакета** фиксирует манифест: что не указано в манифесте, установщик считает ошибкой.

## 9. Выпуск

- **Версии:** `X.Y.Z` — окончательный выпуск; `X.Y.Z-rc.N` и `X.Y.Z-dev.N` — предварительные (pre-release на GitHub).
- **Публикация:** выпуск `vX.Y.Z` в GitHub Releases репозитория выпусков; во вложениях — пакет и `install.sh` из этого
  же пакета. В описании — заметки к выпуску (что изменилось) и сведения о пакете: коммит, время сборки, образы и их
  размеры.
- **Документация** `docs/` обновляется при каждом выпуске из справки кабинета той же версии.
- **Хранение:** окончательные выпуски не удаляются; из предварительных остаются два последних. Любой выпуск можно
  собрать заново из его коммита.
- **Проверка перед публикацией:** чистая установка на стенде через `install.sh` и мастер, затем вход сотрудника на стол;
  рекомендуется и обновление стенда с прежней версии.

## 10. Как проверить происхождение конкретной установки

1. **Пакет:** `tar -xOf cloududs-X.Y.Z.tar manifest.json` — версия, коммит, время сборки, ID образов. Подпись:
   `openssl pkeyutl -verify -pubin -inkey release-pub.pem -rawin -in manifest.json -sigfile manifest.sig`.
2. **Образы на узле:** `docker image inspect cloududs/<образ>:X.Y.Z -f '{{.Id}}'` — совпадает с ID в манифесте.
3. **Версии upstream внутри образов:** брокер — `/opt/uds/VERSION` (коммит OpenUDS), туннель — `/VERSION` (коммит
   туннеля), guacd — `/VERSION`; метка образа `guacamole` — коммит guacamole-auth-uds.
4. **Зависимости:** кабинет → «Уязвимости» — опись пакетов узлов и образов с находками по базе OSV; у туннеля опись — по
   его `Cargo.lock`.
5. **Лицензии сторонних компонентов** — NOTICE.md в репозитории выпусков; тексты лицензий — внутри соответствующих
   образов.

## 11. Ограничения воспроизводимости

Выпуск прослеживается до коммитов, но собран не полностью воспроизводимо — повторная сборка того же коммита может дать
другие байты:

- базовые образы берутся по тегам (`ubuntu:24.04`, `python:3.12-slim-bookworm`, `tomcat:9.0-…` и др.), а не по
  дайджестам — так в образы попадают свежие исправления безопасности;
- Python-зависимости кабинета и мастера закреплены с точностью до минорной версии (`fastapi==0.142.*`), не до файла;
- агент UDS и клиенты собираются вне сборочной машины; коммит исходников агента UDS в пакет пока не записывается, а
  инструменты сборки клиентов (Rust, vcpkg, Homebrew) берутся актуальных версий на момент сборки.

Что именно попало в выпуск, фиксируют манифест (ID образов, SHA-256 файлов) и опись пакетов в «Уязвимостях».
