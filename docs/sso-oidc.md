# Вход через IdP организации (OpenID Connect) и вход без пароля

*Руководство администратора → Безопасность*

> Keycloak, Blitz Identity Provider, Entra ID: сотрудник входит через IdP организации, а если IdP пускает по ключу доступа (Touch ID, телефон, Windows Hello), — вся цепочка до Windows без пароля.

## Что получается

На странице входа появляется кнопка «Войти через …». Пароль, второй фактор и ключи доступа проверяет IdP организации, портал получает подтверждённый ID-токен. С включённой связью с доменом это тот же доменный пользователь, что и при входе по паролю: те же столы и группы из AD. Windows на столе пускает по сертификату («Вход на стол без пароля»), поэтому, если IdP пустил по ключу доступа, пароль не вводится нигде.

| Звено | Чем подтверждается |
|----|----|
| Портал | IdP: пароль, второй фактор или ключ доступа (passkey) |
| Клиент CloudUDS | билет портала |
| Windows на столе | сертификат входа со смарт-картой, выданный на один сеанс (Kerberos PKINIT) |

## Как это работает

1.  Портал перенаправляет сотрудника в IdP (поток «authorization code», OpenID Connect).
2.  IdP проверяет сотрудника и возвращает одноразовый код на адрес возврата портала.
3.  Портал обменивает код на ID-токен, используя секрет клиента, и проверяет подпись токена сертификатом IdP, получателя (ID клиента) и одноразовое значение nonce.
4.  Имя пользователя из токена сопоставляется с доменной учётной записью; группы берутся из AD.

## Настройка IdP

1.  Заведите **конфиденциального** клиента OpenID Connect с потоком «authorization code».
2.  Адрес возврата (redirect URI): `https://<портал>/uds/page/auth/<метка>` — точный адрес покажет форма подключения в кабинете.
3.  Адрес после выхода: `https://<портал>/my/login`.
4.  В ID-токен: имя пользователя (`preferred_username` или `upn`), группы (`groups`, без пути) и полное имя (`name`).
5.  Пользователи IdP — из того же AD: отключённая в AD учётная запись не должна входить в IdP (в Keycloak — фильтр по `userAccountControl`).
6.  Несколько контроллеров домена и быстрое переключение: в Keycloak укажите все контроллеры, выключите пул соединений LDAP и задайте тайм-ауты (подключение 3 с, чтение 10 с). Иначе при отказе одного контроллера вход висит минутами. Пароли IdP не хранит: без контроллеров вход по паролю невозможен, а столам контроллер нужен всё равно.

> **Keycloak.**
>
> Издатель — `https://<сервер>/realms/<realm>`. Пользователи — «User federation» → LDAP (AD, только чтение). Чтобы входили и по `ivanov`, и по `ivanov@company.ru`, сопоставьте `userPrincipalName` с адресом почты и включите вход по почте. Консоль администратора не публикуйте наружу (`KC_HOSTNAME_ADMIN` — внутреннее имя).

## Подключение в кабинете

1.  «Единый вход» → **«Подключить OpenID Connect»**.
2.  Название на кнопке и метка, адрес издателя (issuer) — кнопка «Прочитать описание» покажет, что нашлось у IdP.
3.  ID клиента и секрет, «Связать с доменом организации».
4.  Сохраните и нажмите **«Проверить»**: описание IdP, адреса, ключи подписи и их сроки, знает ли IdP клиента и адрес возврата, верен ли секрет, связь с доменом.

> **Ключи подписи IdP.**
>
> IdP время от времени меняет ключи подписи. Портал перечитывает их раз в час сам и присылает уведомление, когда они сменились; вручную — «Обновить ключи и адреса».

## Вход без пароля: ключи доступа

Ключ доступа хранится на устройстве сотрудника и привязан к адресу IdP. Подходят Touch ID и Face ID (связка ключей iCloud), телефон рядом с компьютером (QR-код и проверка близости по Bluetooth), Windows Hello, ключи FIDO2 (в том числе Рутокен MFA).

1.  В IdP включите вход по ключу доступа (в Keycloak — «WebAuthn Passwordless Policy», «Enable Passkeys», проверка пользователя обязательна).
2.  Сотрудник один раз входит паролем и регистрирует ключ. В Keycloak — по ссылке `…/realms/<realm>/protocol/openid-connect/auth?client_id=account-console&redirect_uri=…/account/&response_type=code&scope=openid&kc_action=webauthn-register-passwordless` (в аккаунте Keycloak пункта нет, пока ключ доступа не добавлен в поток входа отдельным шагом).
3.  Дальше — «Войти через …» → ключ доступа: без имени и пароля.
4.  Ключ регистрируется **один раз на связку**: в iCloud или Google он сам появится на остальных устройствах. Чужой компьютер (например, Windows без вашей связки) — «войти с телефона»: QR-код и Bluetooth, а не новая регистрация.
5.  На портале — ссылка «Ключ доступа» в шапке, если её включить в подключении («Единый вход» → OpenID Connect).

> **Потерян телефон.**
>
> Администратор IdP удаляет ключи сотрудника; сотрудник входит паролем со вторым фактором и регистрирует новый.

## Если не работает

| Что видно | Причина | Что делать |
|----|----|----|
| «Invalid username or password» в IdP с `имя@домен` | IdP знает пользователя по короткому имени | войти коротким именем или включить вход по UPN (см. Keycloak выше) |
| «Unknown user authenticated by the Passkey» | на устройстве ключ, которого IdP не знает: регистрация второй раз с другого устройства той же связки (iCloud, Google) заменила ключ, а IdP её отклонил | администратор IdP удаляет ключ сотрудника, сотрудник удаляет ключ в «Паролях» и регистрирует один раз; на другие свои устройства ключ приедет через связку |
| IdP пишет «Invalid redirect uri» | в клиенте IdP другой адрес возврата | скопировать адрес из формы подключения |
| После IdP — «нет доступа к рабочим столам» | у пользователя нет групп с доступом в домене | добавить в группу пула в AD |
| Перестало пускать всех сразу | IdP сменил ключи подписи, а портал ещё не перечитал | «Обновить ключи и адреса», затем «Проверить» |
| Windows спрашивает пароль | не настроен вход на стол без пароля или старый клиент | раздел «Вход без пароля», клиент CloudUDS |
