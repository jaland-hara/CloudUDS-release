# Пароли и секреты

*Справочник*

> Где система хранит пароли, ключи и токены, как они передаются и что делать при утечке.

## Правила

- Пароли, ключи и токены **не возвращаются в браузер**: поле показывает «задан», пустое поле при сохранении значит «не менять».
- Секреты в базе кабинета зашифрованы **мастер-ключом кабинета** (AES-256-GCM). Мастер-ключ — файл на узлах панели, в базу не попадает: дамп базы без него бесполезен.
- Токены узлов принимаются **только с адреса своего узла**, а в базе кабинета хранится лишь их SHA-256.
- Закрытые ключи узлов (сертификат mTLS, ключ агента фронта) создаются на самом узле и **не покидают его**.
- Подключение узлов — одноразовым кодом (15 минут, привязан к IP) с закреплённым ключом сертификата портала; по SSH пароль и ключ живут только в памяти.
- Резервные копии шифруются **ключом восстановления**, который есть только у администратора.
- **Портал сотрудников — отдельный контейнер**: в нём нет мастер-ключа, кабинета и фоновых задач, а его учётная запись базы (vdiportal) видит только нужные таблицы — администраторов, сессии, ключи и токены не видит и настройки менять не может. Учётной записи UDS у портала нет: каталог столов он читает из «витрины», которую публикует кабинет (без паролей и ключей), доменный пароль меняет входом самого сотрудника, а пароль собственного пользователя — через кабинет, который сам проверяет текущий пароль. Уведомления портал ставит в очередь, отправляет их кабинет.
- **Контейнеры запущены с ограничениями**: без привилегий ядра (keepalived — только сетевые и для своего скрипта), без повышения прав через setuid, корневая файловая система только для чтения, лимит процессов.

## Где хранятся

| Секрет | Где | Как защищён |
|----|----|----|
| **Мастер-ключ кабинета** | /etc/vdi-panel/panel_key.secret на каждом узле панели (секрет роли PANEL_SECRET_KEY, кладёт установщик) | файл только для root и контейнера панели; в базу не пишется; копия — внутри резервной копии (под ключом восстановления) |
| **Ключи сертификатов сайта, ключ ACME, токен Cloudflare, учётная запись VK Cloud DNS** | база кабинета | зашифрованы мастер-ключом; на фронт ключ сертификата уходит зашифрованным под ключ агента этого фронта (X25519) |
| **Пароли VRRP групп туннелей, ключ CA узлов (mTLS), ключи S3 профилей и копий** | база кабинета (настройки) | зашифрованы мастер-ключом |
| **Пароль SMTP и токен Telegram уведомлений, секрет второго фактора администраторов** | база кабинета | зашифрованы мастер-ключом |
| **Пароли подключений к облаку и vCenter, учётки чтения каталога и ввода в домен, шлюзов SMS и почты второго фактора** | база UDS — объекты UDS (провайдеры, аутентификатор, менеджер ОС, второй фактор) | кабинет передаёт их в UDS по REST и у себя не хранит; UDS хранит поля паролей зашифрованными своим ключом (UDS_SECRET_KEY / UDS_RSA_KEY в секретах роли брокера) |
| **Пароли сотрудников** | не хранятся — проверяет контроллер домена | у собственных пользователей UDS — только хеш в базе UDS |
| **Секреты ролей: пароли баз, ключи UDS, пароль keepalived фронтов** | /etc/vdi/secrets.env, /etc/vdi/secrets.d/ на узлах (кладёт установщик) | только root (600); в репозитории и образах их нет |
| **Токен туннеля и шлюза HTML5 (регистрация в UDS)** | /etc/vdi/tunnel/udstunnel.conf (только пользователь туннеля и root, 400), /etc/vdi/guac/guacamole.properties (600) | брокер принимает токен только с IP узла (патч брокера); отзыв — «Отозвать» сервер |
| **Токены агентов узлов, фронтов и агентов нагрузки** | /etc/vdi/{nodeagent,certsync,hostagent}/config.json (600) | в базе кабинета — только SHA-256; принимаются только с адреса узла |
| **Ключ сертификата узла (mTLS)** | /etc/vdi/mtls/node.key на туннеле или шлюзе (600) | создаётся на узле, в кабинет уходит только запрос на подпись (CSR) |
| **Токены агентов на столах, ключи скриптов подготовки эталонов** | база кабинета | токен — на один стол; ключ подготовки — одноразовый |
| **Ключ восстановления копий** | только у администратора (показан один раз) | кабинет хранит открытую половину и может лишь шифровать |

## Как передаются

Внутри контура трафик идёт по серым сетям, доступ к портам ограничен группами безопасности. TLS снаружи заканчивается на фронтах.

| Канал | Защита |
|----|----|
| **Браузер и клиент UDS → фронты** | HTTPS, TLS 1.2 и выше, сертификат сайта |
| **Интернет → пограничные фронты → внутренние** | TCP-проброс без расшифровки (PROXY v2): TLS сотрудника расшифровывается только на внутренних фронтах |
| **Фронты → брокеры, панели, шлюзы HTML5** | HTTP внутри контура; заголовок с адресом клиента принимается только от фронтов |
| **Кабинет → REST UDS** | HTTP к брокерам внутри контура, служебная учётная запись кабинета |
| **Портал → база кабинета** | отдельная учётная запись vdiportal с правами только на заявки, журнал аудита, учёт неудачных входов, очередь уведомлений и чтение настроек и образов |
| **Брокеры и кабинет → Galera; репликация Galera** | протокол MariaDB внутри контура, пароли из секретов ролей |
| **Брокер → контроллеры домена** | LDAP или LDAPS — выбирается в «Домене»; смена пароля сотрудником работает только по LDAPS |
| **Туннель и шлюз HTML5 → брокер** | HTTPS через фронты, токен + адрес узла; с сертификатами узлов (mTLS) — порт 8444 и сертификат узла, «Требовать» закрывает эти адреса на 443 |
| **Клиент → туннель → стол** | TLS туннеля; RDP до стола внутри контура |
| **Агенты узлов и фронтов → кабинет** | через портал (HTTPS) или напрямую к узлам панели, токен + адрес узла |
| **Агенты на столах → кабинет** | HTTPS через портал, токен стола |
| **Профили и копии ↔ S3** | HTTPS по временным подписанным ссылкам: ключей S3 на столах и узлах нет; копии дополнительно зашифрованы |
| **Уведомления** | SMTP с SSL или STARTTLS; Telegram — HTTPS |
| **События в SIEM** | syslog по TLS или HTTPS — по настройке «Журнала» |
| **Журналы** | токены в адресах шлюзов HTML5 маскируются в журнале HAProxy, коды подключения — звёздочками |

## Если секрет утёк

| Что | Что сделать |
|----|----|
| **Токен туннеля или шлюза** | «Размещение» → «Отозвать» сервер и подключить узел заново: новый токен, сертификат узла отзывается сам |
| **Ключ узла (mTLS)** | «Сертификаты» → «Сертификаты узлов» → «Перевыпустить»: узел создаст новый ключ за минуту |
| **Пароль служебной учётки (домен, облако, vCenter, DNS, S3)** | сменить в источнике и ввести новый в кабинете |
| **Ключ восстановления** | «Резервное копирование» → новый ключ и сразу новая копия; старые копии удалить из бакета |
| **Мастер-ключ кабинета или секреты ролей** | смена — через установщик (перешифровка базы кабинета и раскатка по узлам); пока выполняется вручную по инструкции |
